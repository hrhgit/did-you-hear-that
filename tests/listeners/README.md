# tests/listeners

Simulated listeners used by the property tests. A listener is a function from "a sound at this level on this side" to a response, with a chosen threshold for each ear. Any randomness in a listener comes from a seeded generator, so a run can be replayed.

- **Listener types.** `listener-types.ts` defines what a listener sees: the kind of trial, and for a sound its ear and level. `psychometric-listener.ts` is the imperfect listener, with a true threshold per ear, a psychometric width, and lapse, false alarm and wrong-side rates. `extreme-listeners.ts` holds the listeners that behave badly on purpose: always answers, never answers, answers at random, always names the wrong side, always presses left. `listener-parameter-arbitraries.ts` holds the Plausible and Attentive parameter ranges.
- **The harness.** `search-under-test.ts` is the interface every version of the search is run through, so the same checks work on any version. `spec-search-under-test.ts` adapts this repository's engine to it, and `searches-under-test.ts` lists the searches the scripts can name. `classify-accuracy.ts` says whether an ear result is Accurate (within one step of the level grid around the true threshold), Flagged or Wrong, and `is-within-five-db.ts` keeps the first, 5 dB version of that measure for comparison. `measure-population.ts` and `play-population-rooms.ts` run one room for each listener of a population drawn from one seed.
- **The scatter script.** `write-scatter-data.ts` runs `npm run experiment:scatter` and writes `docs/experiments/threshold-search-scatter-<search>.csv`, true threshold against estimate for 3000 listeners. It is not a test file, so Vitest does not collect it.
- **The simulated visitor.** `simulated-visitor.ts` plays one whole visit through the visit flow with any of the listeners above (`playVisit`). It follows a visitor script: it chooses the visit, starts the hiss and presses louder until the played setting reaches its target, keeps it, plays and answers the headphone check, and goes on from the rules, the rests between rooms and the replay after a rest. It hears of each trial only from the flow's test hook `onTrialPresented`, never from the screen, asks its listener, and answers after a delay drawn from its seeded source, with a time stamp that may be the time now, earlier, missing, not a number or in the future. It also gives the script's extra presses, its pauses and stop reports followed by a resume, and its ending, the stop control or a left page. It moves time by events, to whichever comes first of its next planned step and the timer's next callback, so that every answer lands at the planned moment. The clocks are moved by a driver, which `tests/properties/visit-flow-harness.ts` provides. `simulated-visitor.test.ts` plays one quick visit with a step listener and checks that every caught trial is a sound at or above the listener's threshold.
- **The measurement of the visit-level rule.** `visit-rule-measurement.ts` (`measureVisitFalseAlarmRule`) plays whole quick and full visits room by room through the shipped engine with psychometric listeners and fixed seeds, judges every ear with `classifyAccuracy`, and applies the session's `judgeVisitFalseAlarms` at each candidate limit. `print-visit-rule-measurement.ts` runs it for the cases of the visit-flow design and prints the tables as Markdown. It writes no file and has no `package.json` script:

  ```
  npx tsx tests/listeners/print-visit-rule-measurement.ts
  ```

  The tables are what the project owner chooses the visit limit from. The limit in config, 0.2, is a proposal that awaits that choice (Q1 in `.kiro/specs/visit-flow/design.md`). Neither file is a test file, so Vitest does not collect them. The statistical property CP11 calls the same function.
