# tests/properties

Property-based tests written with fast-check and run by Vitest under Node. Files are named `*.property.test.ts`.

When a property finds a counterexample, fast-check prints its seed and the shrunk case. Keep that case as a named regression test, and put the fix in a separate commit.

- **`checks/`** holds one module per correctness property of the threshold search, shared by the Vitest files and by `npm run experiment:properties`, which writes `docs/experiments/brief-properties-<search>.json`. Modules marked harness-neutral run against any search through `tests/listeners/search-under-test.ts`. The others check this repository's own engine only. `ear-oracle.ts` re-derives an ear's result from its trial records without calling the engine.
- **The regression file.** `threshold-search-regressions.test.ts` holds one case per counterexample, named `regression <n>: <what went wrong> (<property>, seed <s>)`, with hard-coded listener parameters and seeds. A case is first committed on its own with Vitest's `it.fails`, which marks an expected break and keeps the suite green. The commit that changes the code turns it into an ordinary `it`. A case whose only remedy would move a value that may not be moved silently stays an expected break, with a decision in `.kiro/specs/threshold-search/design.md` giving the measured numbers.
- **Seeds.** Universal properties run with a new random seed every time, so each run explores new cases. Statistical properties, which judge rates over many simulated rooms, run with fixed seeds and fixed limits, so a change in their verdict comes from the code and not from the draw.

## The visit flow

The properties CP1 to CP11 of `.kiro/specs/visit-flow/design.md` are in `visit-flow-cp<n>-*.property.test.ts`. Each plays whole visits through the visit flow under Node, with no browser.

- **The visit harness.** `visit-flow-harness.ts` (`createVisitHarness`) builds a visit flow on the fake audio backend and the manual timer. The page clock runs ahead of the audio clock by an offset drawn per run, from 0 to 10⁶ ms, so that no code can assume the two are equal, and the harness moves both clocks together. It records every snapshot notification and event with its time and its cause (an action, a stop report or a timer callback), every presented trial, every action, and every `schedule` call on the backend. With `spyOnOutput` it also wraps the output shell in a spy that records the flow's calls to it. The files that use it replace the synth's render functions with the worst-case renderers of `worst-case-renderers.ts` through `vi.mock`, so a visit takes milliseconds. `visit-flow-timeline.ts` (`observeVisit`) puts the harness's separate records in one ordered list, with the snapshot before and after each action and stop report, for the properties that ask what came before what.
- **The visitor scripts.** `visit-flow-arbitraries.ts` draws what a simulated visitor does in one visit: the visit type, a calibration target, the first answer to the headphone check, a listener (psychometric, one of the extreme listeners, or any function of the trial), answer delays that sometimes fall after the window, time stamp modes, extra presses, up to four pauses or stop reports each followed by a resume, at most one ending, and rests of up to 30 s before each step on. `tests/listeners/simulated-visitor.ts` plays the script.
- **Simulated visits.** `visit-flow-simulated-visits.test.ts` plays a quick and a full visit to the result with fixed seeds, for an attentive and a plausible listener and for each extreme listener.
- **The regression file.** `visit-flow-regressions.test.ts` holds one case per counterexample a visit flow property finds, named and handled as in the regression file of the threshold search above. A case that only a change of a steering value or of the proposed visit limit (Q1) could remove stays an expected break. It holds one `it.todo` until the first case is found.

The `screen-leak/` folder has its own README, `screen-leak/README.md`.
